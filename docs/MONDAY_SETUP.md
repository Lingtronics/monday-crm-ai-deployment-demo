# monday setup and live verification — not yet performed

`LIVE_MONDAY_VERIFIED=false`. There is no token, account subscription evidence, sandbox ID, discovered mapping or live test result in this delivery. Adapter tests intercept fetch. The commands below are an onboarding checklist, not evidence that live integration works.

1. In an **existing authorised account**, inspect actual product, subscription, API permissions, board allowance, relation availability and automation/integration entitlement. Do not activate a trial or paid feature. If unavailable, retain Mode C. Free-capable Plan B needs three boards; trial-capable Plan A adds Contacts only if permitted. Record capability findings locally without exposing unrelated data.
2. Manually create or select a workspace named exactly **CRM Demo | Northstar Sandbox** containing synthetic demo work only. Copy its workspace ID from the UI. Do not supply an unrelated workspace. Place your own personal token in local `.env` or the shell; never paste tokens into chat/source/logs. The token inherits your UI access ([authentication](https://developer.monday.com/api-reference/docs/authentication)).
3. Copy `.env.example` to `.env` if not already present. Set MODE=monday, MONDAY_API_TOKEN and MONDAY_WORKSPACE_ID locally. Keep DEMO_WRITE_ENABLED=false. Run `pnpm setup:monday --dry-run` (or add `--plan-a`) to review the proposed board/column manifest. This dry run makes no requests and does not claim account validation.
4. If the workspace already has matching demo boards, copy their IDs into comma-separated MONDAY_ALLOWED_BOARD_IDS before execution. Only exact `CRM Demo | Leads`, `CRM Demo | Accounts`, `CRM Demo | Opportunities`, and optionally `CRM Demo | Contacts` names are reused. Duplicate matching names stop provisioning. No existing non-allowlisted board schema is inspected or modified. Discovery reads board names/IDs in the explicitly selected sandbox workspace only.
5. When the reviewed destination is correct, set DEMO_WRITE_ENABLED=true locally. Run `pnpm setup:monday --execute` (Plan B), or `pnpm setup:monday --execute --plan-a`. The script verifies the exact workspace name/ID first, reuses matching boards, creates missing demo boards/columns and saves returned IDs in `config/column-map.json`. New returned board IDs are temporarily allowlisted during that run. No deletion or overwrite of existing status labels occurs. On API errors or ambiguous outcomes, stop and reconcile; do not repeatedly clear local state.
6. Copy the output board IDs into MONDAY_LEADS_BOARD_ID, MONDAY_ACCOUNTS_BOARD_ID, MONDAY_OPPORTUNITIES_BOARD_ID, optional MONDAY_CONTACTS_BOARD_ID, and MONDAY_ALLOWED_BOARD_IDS. The mapping file is generated and ignored by version control; never fabricate column IDs. Re-running setup requires this updated allowlist. If provisioning stopped halfway, use the UI to identify only the newly created named demo boards, allowlist them, then rerun; journals protect uncertain creates.

7. Relations are conditional on actual privileges. In Leads, add a Connect Boards column named Related Account; configure its target to the discovered Accounts board **before linking items**. For Plan A add Related Contact targeting Contacts; in Contacts configure Related Account; in Opportunities configure Related Lead and Related Account. Confirm each target-board setting in UI, not merely column existence. The [official relation documentation](https://developer.monday.com/api-reference/reference/connect) requires configured target boards. Run `pnpm setup:monday --execute --discover-relations` (plus `--plan-a` when applicable) to rediscover Lead relation column IDs/settings; it will fail on ambiguous target relations. The adapter populates discovered Lead→Account and Lead→Contact links. Contact→Account and Opportunity→Lead/Account native links remain manual; local UUID relations cover them. If restricted, omit native relation columns and document SQLite as the fallback; do not claim four natively connected boards.
8. Set DEMO_WRITE_ENABLED=false and run `pnpm smoke:monday`. It reads current API version/user ID, verifies allowlisted schemas/workspace and paginates review values. Output `liveReadSchemaVerified=true` proves only that specific read smoke passed; it explicitly does not prove a write workflow. Pinned `API-Version: 2026-07` is checked against returned version. Record any incompatibility with [official versioning](https://developer.monday.com/api-reference/docs/api-versioning) before changing code/config.

HTTP/local acceptance alone is insufficient. `pnpm seed --dry-run` previews optional larger synthetic seed; `pnpm seed --execute` is gated and rerunnable. No need to seed all cases for the smoke.

Inspect exactly one **internal Lead update**, containing the unique operation marker; this is the follow-up work instruction. Poll again and require no extra update. Stage must remain New. The app never emails or mentions anyone.

Confirm local review/execution/sync states and audit. Capture actual board screenshots with credentials and unrelated details excluded. Only after these steps pass should the capability log say a live workflow was verified; include date, sandbox IDs and observations.
12. Stop the poller/server and reset DEMO_WRITE_ENABLED=false. No cleanup/deletion script exists. Preserve local database/journal and mapping for safe reconciliation. Use the handover guide for failures. Make/native features are a separate checklist.

Exact operational limits: setup uses public boards within the explicit sandbox workspace, subject to account permission; it does not configure sharing or invite users. Account matching is domain-based locally; unknown domains stay separate. No native automation is assumed. Board-created leads need a stable External ID and a mapped synthetic enquiry message passed through authenticated intake; polling only handles reviews for locally known leads, not automatic intake of every board item.

If a matching email is already present remotely under a different External ID but is unknown to the local database, the adapter blocks creation with REMOTE_EMAIL_DUPLICATE_RECONCILE_LOCALLY and records Pending sync. It does not silently import or merge that remote record. Resolve the sandbox record/local mapping manually before retrying. Preserve the local database between live runs so email aliases and account IDs remain stable.
